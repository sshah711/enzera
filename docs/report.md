## Abstract

Electricity theft (meter tampering, bypassing, illegal connections) causes large non-technical losses for utilities.
Inspecting every customer is impossible, so utilities need a ranked list of suspicious customers with a reason for each
flag. ENZERA scores customers for theft risk from their daily smart-meter readings, explains every score with exact
TreeSHAP contributions, adds an unsupervised abnormal-consumption score, and supports the inspection workflow in a
deployed web application. On the SGCC dataset (42,372 customers, 1,034 days, 8.53% theft), our XGBoost model on
14 engineered features reaches ROC-AUC 0.788 and PR-AUC 0.332 on a held-out test set. If inspectors visit only the 10%
of customers with the highest scores, they find 40.5% of all thieves (random selection: 10%). SMOTE and alternative
hyperparameters did not improve on this model. The system is deployed as a FastAPI backend on Render and a Streamlit
frontend on Streamlit Community Cloud, with automated tests and CI.

## 1. Introduction and problem

**Background.** Losses in electricity distribution are either *technical* (energy lost in lines and transformers)
or *non-technical*, mainly theft. Smart meters (Advanced Metering Infrastructure, AMI) record each customer's
consumption every day. This creates the data needed to detect theft automatically from consumption patterns.

**Problem.** Given a customer's daily consumption history, estimate the probability that the customer is stealing
electricity, so that a limited number of field inspections can be focused on the most suspicious customers.

**Why it is hard.**
1. **Class imbalance**: only 8.53% of SGCC customers are labelled as thieves.
2. **Messy data**: 25.7% of readings are missing in our training split, often in long blocks.
3. **Overlap**: thieves and normal customers have similar consumption profiles (no single feature reaches an ROC-AUC
   above 0.71 on its own; Section 3).
4. **Trust**: an inspector will not act on a bare score. Each flag needs a reason that can be checked.

**Objectives.**
- Build a supervised theft-risk model and compare it with simple baselines using imbalance-aware metrics.
- Add an unsupervised detector for *abnormal* consumption that needs no labels.
- Explain every individual prediction (SHAP).
- Deliver a working product: REST API, database of inspection cases, web dashboard, deployment and CI.
- Evaluate honestly: tune the threshold on validation data, report on a held-out test set, and show the app only
  customers the model never saw.

## 2. Literature review

**Zheng et al. (2018), Wide & Deep CNN on SGCC.** Zheng, Yang, Niu, Dai and Zhou released the SGCC dataset used in this
project (daily consumption of 42,372 customers from the State Grid Corporation of China, January 2014 - October 2016,
with theft labels). Their model has two parts. The *Wide* part is a fully connected network on the raw 1-D daily series,
which learns global patterns. The *Deep* part is a convolutional neural network applied to the consumption reshaped into a
2-D matrix of weeks × days, which captures weekly periodicity and how it is disrupted. They pre-process the data by
interpolating missing values and capping outliers. Our cleaning step follows the same idea: interpolation and a 3-sigma
cap (Section 4). They evaluate with ROC-AUC and MAP@N (precision among the top-N ranked customers), which, like our
"theft caught in the top 10%", reflects how inspections are actually planned.
*Relation to our work:* we use their dataset and their insight that periodicity and changes in consumption over time carry
the theft signal. Instead of a deep network, we encode these signals as 14 interpretable features and use gradient-boosted
trees, which train in minutes on a CPU and give exact per-customer explanations. Our results are not directly comparable to
theirs because the train/test splits and protocols differ.

**Jokar et al. (2016), theft attack types.** Jokar, Arianpoo and Leung studied theft detection in AMI using customers'
consumption patterns. They formalised a set of *false-data injection attack* types, i.e. ways a thief can manipulate
reported consumption: reducing readings by a constant or random factor, reporting zero during certain periods, reporting
a constant (for example the average) value instead of the real profile, and re-ordering the true readings so that the
total stays the same but the cost under time-of-use pricing drops. They used these synthetic attacks to train and test a
classifier (support vector machine) on each customer's consumption pattern.
*Relation to our work:* several of our features directly target these attack families. `max_monthly_drop`,
`recent_vs_past`, `trend_slope` and `low_day_ratio` respond to factor-reduction attacks. `zero_ratio` and
`longest_zero_run` respond to zero-reporting attacks. `cv_daily`, `std_daily` and `monthly_cv` respond to
constant-value attacks (abnormally low variability) as well as erratic behaviour. Unlike Jokar et al., we train on real
inspection labels rather than synthetic attacks, and we do not have time-of-use (sub-daily) data, so re-ordering attacks
within a day cannot be detected.

**References**

1. Z. Zheng, Y. Yang, X. Niu, H.-N. Dai and Y. Zhou, "Wide and Deep Convolutional Neural Networks for Electricity-Theft
   Detection to Secure Smart Grids," *IEEE Transactions on Industrial Informatics*, vol. 14, no. 4, pp. 1606-1615, 2018,
   doi: 10.1109/TII.2017.2785963.

## 3. Dataset and exploratory data analysis

**Dataset.** `data/raw/data.csv`: one row per customer with `CONS_NO` (anonymised ID), `FLAG` (1 = theft, 0 = normal)
and 1,034 daily consumption columns (kWh) from 2014-01-01 to 2016-10-31. The date columns are **not stored in date order**
in the file (e.g. `2014/1/1, 2014/1/10, 2014/1/11, ...`). `ml/features.split_wide()` parses and sorts them. Without this
step, every time-based feature would be wrong.

| Property | Value |
|---|---|
| Customers | 42,372 |
| Days | 1,034 |
| Theft rate | 8.53% |
| Split (stratified, seed 42) | 29,660 train (70%) / 6,356 test (15%) / 6,356 demo (15%) |
| Train split used for fitting / validation | 25,211 / 4,449 |

**Why three splits?** *Train* fits the models (with 15% held back as *validation* to choose the decision threshold).
*Test* is used once for the reported metrics. *Demo* customers are never seen in training or evaluation. 1,000 of them are
loaded into the deployed app, so everything shown in the demo is a genuine out-of-sample prediction.

All EDA below uses the **train split only** (`notebooks/01_eda.ipynb`), so nothing learned from EDA leaks into evaluation.

**3.1 Class imbalance.** 27,130 normal vs 2,530 theft customers (1 : 10.7). A model that always predicts "normal" would be
91.5% accurate and catch no thieves, so we do not use accuracy.
[FIGURE: reports/eda_class_balance.png]

**3.2 Missing data.** 25.7% of all readings are missing, and every customer has at least one missing day. The distribution
has two peaks: most customers miss under 10% of days, but a large group misses about 71% of days. These customers have
**no reading at all before 2016** (22.3% of train customers; 730 of the 1,034 days). On a typical day in 2014-2015 about
35% of customers are missing; in 2016 only 1.6% are. Thieves miss more (median missing ratio 21.4% vs 9.7%), so
`missing_ratio` is kept as a feature.
[FIGURE: reports/eda_missing.png]

**3.3 Zero usage.** Zero-consumption days are rare in both classes (median 0.7% normal, 0.3% theft). In SGCC, theft is
not mainly visible as long zero runs.

**3.4 Thieves vs normal customers.** Counter to the textbook picture of a thief "using less", theft-labelled customers
consume **more**: median of customer means 8.32 vs 5.19 kWh/day (means 27.16 vs 7.69, pulled up by a few very large
consumers). They are also more variable, and their usage rises more in 2016. Both classes share the same seasonal shape.
A plausible explanation (which we cannot verify) is that inspections, and therefore labels, are focused on larger and
more irregular customers.
[FIGURE: reports/eda_avg_consumption.png]

**3.5 Single-feature separation.** ROC-AUC of each feature on its own (train split): `std_daily` 0.705, `max_daily` 0.693,
`mean_daily` 0.654, `recent_vs_past` 0.613, `trend_slope` 0.612, `monthly_cv` 0.593, `cv_daily` 0.575, `missing_ratio` 0.568,
`spike_ratio` 0.547, `low_day_ratio` 0.540, `max_monthly_drop` 0.539, `weekend_ratio` 0.527, `longest_zero_run` 0.466,
`zero_ratio` 0.462. Every feature is weak alone, which motivates a model that combines features non-linearly.

**3.6 Sample curves.** Real curves are messy: flat interpolated stretches for customers without pre-2016 data, a theft
customer whose usage collapses to near zero for almost two years and then recovers, and a theft customer that reads zero
every day.
[FIGURE: reports/eda_sample_curves.png]

## 4. Preprocessing and the 14 features

All preprocessing lives in `ml/features.py` and is shared by training **and** the backend, so deployed predictions use
exactly the same code as training.

**Cleaning (`clean`)**
1. Missing days are linearly interpolated along time (in both directions), and anything still missing becomes 0.
2. Negative readings are clipped to 0.
3. Outliers are capped per customer at mean + 3 standard deviations.

**Input formats.** The API accepts the SGCC wide format or a long format (`customer_id, date, consumption`), which is
pivoted to wide. Customers whose readings are all missing are kept (a bug we found and fixed: `pivot_table` silently
dropped them; a regression test now covers it).

**Features (`compute_features`).** `x` = cleaned daily series of a customer. Monthly means are computed per calendar
month. "Recent" = the last 90 days (or a third of the series if shorter).

| # | Feature | Meaning shown to inspectors | How it is computed |
|---|---|---|---|
| 1 | `mean_daily` | Average daily consumption (kWh) | mean of `x` |
| 2 | `std_daily` | Day-to-day variation (kWh) | standard deviation of `x` |
| 3 | `cv_daily` | Relative variability of consumption | std / mean |
| 4 | `max_daily` | Highest daily consumption (kWh) | max of `x` |
| 5 | `missing_ratio` | Share of days with missing readings | share of raw readings that are NaN (before cleaning) |
| 6 | `zero_ratio` | Share of days with zero consumption | share of days with `x` ≤ 1e-6 |
| 7 | `longest_zero_run` | Longest run of zero-consumption days | longest consecutive run of zero days |
| 8 | `low_day_ratio` | Share of days far below the usual level | share of days with `x` < 0.2 × mean |
| 9 | `spike_ratio` | Share of days with unusual spikes | share of days with `x` > mean + 2 std |
| 10 | `trend_slope` | Long-term trend of monthly usage | least-squares slope of monthly means over time, divided by the mean |
| 11 | `max_monthly_drop` | Largest month-to-month drop | max over months of (m[t-1] - m[t]) / m[t-1], clipped to [0, 1] |
| 12 | `monthly_cv` | Variability between months | std / mean of the monthly means |
| 13 | `recent_vs_past` | Recent usage compared with earlier usage | mean of last 90 days / mean of earlier days, clipped to [0, 10] |
| 14 | `weekend_ratio` | Weekend vs weekday usage | weekend mean / weekday mean, clipped to [0, 10] |

The features fall into four groups: **level** (1, 4), **variability** (2, 3, 9, 12), **suspicious low usage** (6, 7, 8, 11),
**change over time** (10, 11, 13), plus **data quality** (5) and **weekly pattern** (14). The plain-language labels in the
middle column are exactly what the app shows as "reasons".

## 5. Models

All models use the same features and split (`ml/train.py`, seed 42).

| Model | Role | Settings | Imbalance handling |
|---|---|---|---|
| Logistic Regression | linear baseline | StandardScaler + LR, max_iter 2000 | `class_weight="balanced"` |
| Random Forest | non-linear baseline | 300 trees, min_samples_leaf 2 | `class_weight="balanced_subsample"` |
| **XGBoost** | **main model** | 400 trees, max_depth 5, learning_rate 0.05, subsample 0.8, colsample_bytree 0.8, eval_metric aucpr | `scale_pos_weight` = #normal / #theft in the fitting set = **10.721** |
| Isolation Forest | abnormal consumption | 300 trees, contamination "auto", fitted on **normal** training customers only | not needed (unsupervised) |

**Why XGBoost?** Gradient-boosted trees are the standard strong choice for tabular data. They model non-linear effects and
feature interactions (needed because each feature is weak alone), are robust to feature scale and skew, train in seconds on
a CPU, and support **exact TreeSHAP** explanations through `pred_contribs=True`, so no extra library is needed in production.

**Imbalance handling.** `scale_pos_weight` multiplies the loss of each theft example by 10.7, so both classes carry equal
total weight during training. We also tested SMOTE (synthetic oversampling) in `notebooks/02_experiments.ipynb`; it was
worse (Section 6.3).

**Threshold tuning.** Each model outputs a probability. The threshold that turns it into a yes/no flag is chosen to maximise
F1 on the **validation** split (4,449 customers held out from training), never on the test set. For XGBoost the threshold is
**0.673**. The app's risk bands use it: High ≥ 0.673, Medium ≥ 0.337 (half), Low otherwise.

**Isolation Forest.** It isolates points with random splits; points that are isolated in few splits are anomalous. Fitting on
normal customers only means "anomalous" = "unlike a typical normal customer". Raw scores are rescaled to 0-1 using the
1st-99th percentile range on the training split.

**Metrics.** Precision, recall, F1 (at the tuned threshold); ROC-AUC; **PR-AUC** (average precision, the most informative
summary under imbalance; random = 0.085); and **theft caught in the top 10%** (`recall_at_top10`): the share of all thieves found
if inspectors visit the 10% highest-scored customers. This is the metric closest to how a utility actually plans inspections.

## 6. Results

### 6.1 Model comparison (test split: 6,356 customers, 543 thieves)

| Model | Precision | Recall | F1 | ROC-AUC | PR-AUC | Theft caught in top 10% | Precision in top 10% | Threshold |
|---|---|---|---|---|---|---|---|---|
| Logistic Regression | 0.163 | 0.475 | 0.242 | 0.695 | 0.205 | 25.0% | 21.4% | 0.541 |
| Random Forest | 0.324 | 0.354 | 0.338 | 0.776 | 0.293 | 36.6% | 31.3% | 0.257 |
| **XGBoost** | **0.363** | 0.366 | **0.365** | **0.788** | **0.332** | **40.5%** | **34.6%** | 0.673 |
| Isolation Forest | - | - | - | 0.595 | 0.115 | 16.0% | 13.7% | - |

XGBoost is best on every ranking metric. Logistic Regression has the highest recall only because its tuned threshold
flags many more customers, at a precision of 0.163. In the top 10% (635 customers), XGBoost finds 220 of the 543 thieves,
about **4× better than random inspection** (10%).

### 6.3 Experiments: imbalance handling and hyperparameters (`notebooks/02_experiments.ipynb`)

Same split, threshold tuned on validation, test metrics. The "current" row reproduces `metrics.json` exactly.

| Setting | Precision | Recall | F1 | ROC-AUC | PR-AUC | Top 10% | PR-AUC (validation) |
|---|---|---|---|---|---|---|---|
| **Current: class weights** | 0.363 | 0.366 | 0.365 | 0.788 | 0.332 | 0.405 | 0.338 |
| SMOTE (no class weights) | 0.326 | 0.343 | 0.334 | 0.757 | 0.296 | 0.366 | 0.271 |
| HP-A: depth 3, 800 trees | 0.297 | 0.466 | 0.363 | 0.786 | 0.322 | 0.394 | 0.338 |
| HP-B: depth 7, min_child_weight 5, λ 5 | 0.377 | 0.337 | 0.356 | 0.780 | 0.328 | 0.394 | 0.331 |
| HP-C: depth 6, 1500 trees, lr 0.02 | 0.372 | 0.378 | 0.375 | 0.783 | 0.332 | 0.405 | 0.336 |

**Decision rule (fixed before running):** replace the model only if a setting improves test PR-AUC **and** top-10% recall by
≥ 0.01 each, without being worse on validation. No setting qualified, so **the current model is kept**.

- SMOTE is worse on every metric. Because theft and normal customers overlap heavily, synthetic thieves interpolated between
  real ones fall among normal customers and add label noise.
- HP-C ties the current model (PR-AUC difference -0.0009; paired bootstrap 95% CI [-0.015, +0.014]). The simpler 400-tree
  model is preferred.
- Conclusion: with these features, performance is limited by the **features**, not the hyperparameters.

## 7. Explainability

(Full write-up: `docs/explainability.md`.)

**Per-customer explanations.** XGBoost's TreeSHAP (`booster.predict(DMatrix, pred_contribs=True)`) splits each prediction
into one exact contribution per feature plus a base value (0.159 log-odds), and they add up to the model output:
`risk = sigmoid(0.159 + Σ SHAP)`. The app shows the three largest *positive* contributions as reasons.

| Customer (demo split) | Risk | Anomaly | True label | Top SHAP reasons |
|---|---|---|---|---|
| `57531380…` | 0.983 (High) | 1.00 | theft | day-to-day variation 228.11 kWh (+1.75), missing 57% (+0.61), average 220.44 kWh/day (+0.59) |
| `448FE010…` | 0.963 (High) | 0.33 | theft | day-to-day variation 13.86 kWh (+0.80), trend 0.05 (+0.66), missing 29% (+0.33) |
| `50B1489E…` | 0.003 (Low) | 0.27 | normal | only negligible positives; strong negatives: missing 2.4% (-1.15), max 0.71 kWh (-1.13) |

- The first is an extreme, erratic consumer (220 kWh/day, a peak of 905 kWh) with patchy readings.
- The second shows the classic theft pattern: a 65% drop in July 2014, nine months at 3-8 kWh/day, then recovery to 20-57
  kWh/day in 2016.
- The third is a flat 0.5-0.7 kWh/day load with no gaps.

We verified that base value + contributions reproduce each displayed score exactly.

**Global importance** (mean |SHAP| on the test set): missing readings 0.485, day-to-day variation 0.412, highest daily
consumption 0.331, trend 0.293, variability between months 0.216, ... down to share of low days 0.103. Data quality,
magnitude/variability and trend dominate, consistent with the EDA. Importance is not causality: missing readings may
indicate tampering *or* data-collection effects.
[FIGURE: reports/shap_importance.png]

**Isolation Forest.** It is weak as a theft detector (ROC-AUC 0.595, top-10% recall 16.0%). On the 1,000 demo customers its
score is uncorrelated with the risk score (Spearman 0.001), and among the 198 customers with anomaly ≥ 0.5 only 5.1% are
thieves. "Abnormal" is not the same as "theft". Its role is a second, label-free signal for unusual behaviour (new theft
methods, faulty meters), not a ranking for inspections.

**How reliable are the flags?** Using the hidden demo labels: 31 of the 73 High-band demo customers are thieves (42.5%, about
5× the base rate), vs 10.3% in Medium and 4.1% in Low. However, 27 of the 85 demo thieves are scored Low.

**Communication.** The frontend never loads the model. It calls the backend's REST API with `requests` (JSON over HTTPS). The
backend URL comes from the `BACKEND_URL` secret, and an optional `API_KEY` is sent as the `X-API-Key` header.

**API endpoints** (`backend/main.py`, interactive docs at `/docs`)

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | status, model version, number of customers scored |
| GET | `/stats` | customers per risk band, cases per status, threshold |
| GET | `/customers?band=&limit=&offset=` | customers ranked by risk, with reasons |
| GET | `/customers/{id}` | one customer: scores, reasons, full daily series, cases |
| POST | `/predict` | score an uploaded CSV (long or wide; max 10 MB, 2,000 customers, ≥ 30 days) |
| GET | `/metrics` | contents of `reports/metrics.json` |
| GET | `/cases?status=` | list inspection cases |
| POST | `/cases` | open a case for a customer |
| PATCH | `/cases/{id}` | update status (`open`, `theft_confirmed`, `normal`) and notes |

**Quality.** 10 automated tests (`tests/test_enzera.py`) cover date sorting, cleaning, feature signals, long/wide input, the
all-missing-customer regression, and the API (health, ranking, prediction, bad CSV, full case lifecycle). GitHub Actions runs
them plus a Docker build on every push. Frontend errors are explicit: backend asleep or unreachable, timeout, 502-504 while
Render starts, wrong API key.

**Deployment.** Backend: Render Web Service from `backend/Dockerfile` (build context `.`, free plan). Frontend: Streamlit
Community Cloud (`frontend/app.py`, `BACKEND_URL` secret). Local: `docker compose up --build` or two terminals (README).

## 9. Limitations and future work

**Limitations**
- **Moderate accuracy.** Precision and recall are both about 0.36 at the chosen threshold, and a third of demo thieves are
  scored Low. ENZERA prioritises inspections; it does not prove theft.
- **Handcrafted features.** 14 summary features discard most of the temporal detail (e.g. weekly periodicity, which Zheng et al.
  exploit). Experiments show tuning cannot compensate.
- **Interpolation of long gaps.** 22.3% of customers have no data before 2016. Interpolation fills that gap with a flat line,
  which can distort variability and trend features.
- **Label bias.** Labels come from past inspections, so the model learns who was *caught* (apparently larger, more variable
  consumers). Small-load thieves may be under-detected. SHAP importance is correlational, not causal.
- **Isolation Forest** is only slightly better than random at finding theft.
- **SQLite on free hosting resets.** Render's free instance has no persistent disk. The database lives in `/tmp` and is rebuilt
  on every restart or sleep, so inspection cases are lost.
- **Free-tier cold starts.** The backend sleeps after 15 minutes idle and takes about 30-60 s to wake.
- **No authentication or user roles.** The optional single API key is the only protection.

**Future work**
- **Deep models on raw series:** 1D-CNN or LSTM on daily data (and the weekly 2-D layout of Zheng et al.), compared with XGBoost.
- **MLflow model registry:** `ml/train.py` already logs runs when MLflow is installed. Add registered, versioned models and
  promotion rules.
- **Automated retraining from inspection outcomes:** confirmed cases (`theft_confirmed` / `normal`) become new labels. A
  scheduled job joins them with readings, retrains, compares against the current model on a fixed test set, and promotes the
  new model only if it is better.
- **Drift monitoring:** track feature distributions and score distributions over time and alert when they shift.
- **PostgreSQL** (managed) instead of SQLite, for persistent, multi-user case management.
- Authentication and roles for inspectors and managers.

## 10. Conclusion

ENZERA turns raw smart-meter data into a ranked, explained inspection list. On SGCC, an XGBoost model on 14 interpretable
consumption features, with class weights and a validation-tuned threshold, reaches ROC-AUC 0.788 and PR-AUC 0.332, and finds
40.5% of thieves in the top 10% of customers, four times better than random inspection. It also clearly beats Logistic Regression
and Random Forest baselines. SMOTE and alternative hyperparameters did not help, which points to richer temporal features or deep
models as the next step. Every score comes with exact TreeSHAP reasons that an inspector can check against the consumption
curve, and an Isolation Forest adds a label-free abnormality signal. We also found that it is weak for theft ranking. The
complete system (training pipeline, FastAPI backend, Streamlit frontend, tests, CI and cloud deployment) is live and
reproducible from the public repository.
